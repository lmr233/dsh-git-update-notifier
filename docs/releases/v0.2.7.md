## 一、这一版要解决的问题

v0.2.6 让"安装失败"变得可重试、可回退。但**失败原因本身仍然看不清**：

```js
message: `${NPM_COMMAND} install 失败：${tail(result.stderr)}`
```

`tail` 只留最后 6 行。而 npm 与 git 的关键信息经常恰恰不在这 6 行里 —— 例如
`EACCES: permission denied, access 'C:\...'` 出现在前面，后面跟一大段调用栈；
又或者只报"无法快进"，但真正的原因是本地有未提交改动。更要命的是这四件事一样都没记：

- **退出码**：排查时"1 还是 128"是首要线索；
- **执行的命令**：用户不知道插件到底跑了什么、参数是什么；
- **现场**：安装形态、包位置 / 仓库根 / 安装位置、代理、运行时版本 —— 这些决定
  "为什么偏偏在这台机器上失败"；
- **持久性**：错误信息只活在当前这一屏，刷新页面或重启 dsh 之后就没了，
  而"检修"往往发生在事后。

v0.2.7 的目标很直接：**失败时留下完整现场，并且事后还找得回来**。

## 二、交付内容

### 诊断日志（新增 `$DSH_HOME/dsh-git-update-notifier-logs/`）

`resolve` / `download` / `verify` / `install` / `fetch` / `merge` 任一阶段失败都会写一份
`update-<时间>-<阶段>.log`，内容包括：

| 项 | 说明 |
|---|---|
| 时间 / 阶段 / 插件版本 | 定位"哪一次、哪一步" |
| 安装形态 / 包位置 / 仓库根 / 安装位置 | 形态判定错了就是另一个故事 |
| 本地版本 → 目标版本 | 从哪儿到哪儿 |
| 代理 / 运行时 | `node v24.15.0 / win32 x64`；代理是"经代理"还是"未使用" |
| 命令 / 退出码 | 实际执行的整条命令 |
| 完整 stdout / stderr | 每段最多 256 KB，超出会标注截断 |
| `git status --short` | 仅在合并失败时 —— 检修分叉 / 未提交改动最需要它 |

两个约束：**写日志失败绝不影响更新流程**（降级成一条告警），**只保留最近 20 份**
（按修改时间自动清理更旧的）。

### `GET /diagnostics.json`

返回最近一次失败的完整现场 —— 优先取进程内保存的那份（就是刚刚失败的那次），
重启之后回退到磁盘上的诊断文件内容。参数里带路径的地方做了两件事：
`resolve` 之后校验必须落在日志目录内，且内容截断到 256 KB。

### 错误信息带上退出码与命令

`npm install` / `git merge` 的失败消息从"失败：…"变成"**失败（退出码 N）**：…"，
命令与诊断文件路径一并写进 `lastUpdate.diagnostic`（状态文件里只存摘要，
完整输出不放进去 —— 状态文件每次检查都会重写，塞几十 KB 进去会越滚越大）。

### 设置页

任何阶段的失败都会多出：

- 一行现场摘要：`命令：…　退出码：…　诊断日志：<路径>`
- 一个「**查看完整报错**」按钮，点开在页面内摊开完整输出（`<pre>` 里直接复制）

完整输出是**懒加载**的：不点「查看完整报错」就不发请求。

## 三、关键决策与取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| 现场落盘，而不是只放内存 | 检修往往发生在事后，重启 dsh 后还要看得到 | 需要清理策略与"只读日志目录"的路径校验 |
| 状态文件只存摘要 | 状态每次检查都重写，塞几十 KB 输出会持续膨胀 | 完整内容有两个来源（进程内 + 磁盘），要合并 |
| 诊断内容懒加载 | 失败输出可能几十 KB，不该跟着每次 `status.json` 一起发 | 用户要多点一下 |
| 读文件限定在日志目录内 | 接口参数来自 HTTP，任何路径拼接都得设防 | 多一层 `resolve` + 前缀校验 |
| 只留最近 20 份 | 免得日志目录无限增长 | 更早的历史会被自动删掉 |
| 每个失败阶段都写 | 下载 / 校验失败同样要检修（比如镜像到底返回了什么） | 各失败分支变长 |
| 不采集环境变量 | 环境变量里常有 token、代理口令，检修价值不抵泄露风险 | 某些代理问题少一条线索（但代理地址本身已记） |

### 尚未在真机验证的部分（如实记录）

## 五、已知限制

- **诊断输出有上限**：单段 stdout / stderr 最多 128 KB（状态摘要里是 32 KB），
  诊断文件里每段最多 256 KB，超出会明确标注截断。
- **只保留最近 20 份**诊断日志。
- **不采集环境变量**（见上表）。
- 诊断记录的是"这次失败长什么样"，**不修复根因** —— 权限、磁盘、依赖树冲突仍要人来处理。

## 六、开发过程时间线

1. **先定"要记什么"** —— 从排查视角倒推：退出码、命令、形态与路径、代理、运行时、
   完整输出、工作区状态。缺哪一项会让哪一类问题查不下去，逐条对过。
2. **写诊断模块**（`writeDiagnostic` / `pruneDiagnostics` / `clip` / `readDiagnosticFile`）——
   落盘、限份数、截断、路径校验一次做完，避免后面每个调用点各写一份。
3. **加统一的 `diagnose()` 入口** —— 让六个失败分支只需填"现场字段"，写盘与摘要形状
   保持一致（否则很容易出现某个分支忘了带退出码）。
4. **接入各失败分支**：install / merge / fetch / download / verify。其中 merge 失败额外跑了
   `git status --short` 一起记下来 —— 分叉与未提交改动是这一阶段最常见的真实成因。
5. **状态里只存摘要**：`lastUpdate.diagnostic = { file, command, exitCode, phase, at }`，
   完整输出留给内存与磁盘。
6. **`GET /diagnostics.json`**：进程内优先、磁盘兜底，路径做前缀校验。
7. **客户端**：现场摘要行 + 「查看完整报错」（懒加载，点开摊在 `<pre>` 里）。
8. **测试**：`local-check` 补路由与空态；`client-render` 补展示与请求落点；
   `e2e` 第 11 节扩写为"失败 → 诊断文件落盘 → 内容断言 → 接口与状态都能拿到"。
9. **路由数 10 → 11**（`local-check` 与 `e2e` 各一处，本仓库的老约定）。
