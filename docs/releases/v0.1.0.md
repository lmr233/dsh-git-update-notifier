## 一、背景：为什么不是又一个 npm 更新检查器

立项前调研了 GitHub `dsh-plugin` 主题下的同类插件，至少 9 款在做"检查 dsh 更新"，
它们的做法高度一致：对比 **npm registry 上的 `@deepseek-ai/dsh`**。

但在这台机器的实际形态下，这条路是错的：

```
$DSH_HOME/profiles/node_modules/@deepseek-ai/dsh
  → Junction → <checkout>/apps/cli        # 只是指向源码 checkout 的链接
```

dsh 本体跑的是**源码 checkout**（git remote 指向 `deepseek-ai/deepseek-harness`），于是：

- **查 npm 会误报** —— 本地往往是 tag 之后又多走了若干提交的构建，registry 上并没有对应版本；
- **更新动作有破坏性** —— 若"更新"执行 `npm install`，会往源码仓库里装包，破坏 pnpm workspace 的链接结构。

因此 v0.1.0 的目标定为：**只推进源码 checkout 的提交，全程不碰 npm 与 `node_modules`**。

## 二、交付内容

### 宿主端 `lib/index.js`

- **每日首次检查**：按自然日去重（状态文件记录日期），同一天内多次重启不重复检查、不重复打扰。
- **代理自适应**：探测 Windows 系统代理（注册表）与标准代理环境变量，仅在自身的 git 调用里以
  `-c http.proxy=…` 生效，**不修改用户的任何 git 配置**；先试代理、失败回退直连；每次检查重新探测。
- **checkout 定位**：解析 `@deepseek-ai/dsh` 的 `realpath`（穿透 junction / 符号链接）后上溯到含
  `.git` 的目录，**无硬编码路径**。
- **更新执行**：`git pull --ff-only`，只允许快进合并。
- **HTTP 路由**：`status.json`（GET）、`check` / `update` / `dismiss`（POST）。
  三个写操作都要求 loopback 来源，避免局域网客户端触发 git 操作。
- **健壮性**：检查与更新各自有并发互斥；`fetch` 退避重试；每次检查返回**同一组字段**（不适用的显式置 `null`），
  避免「旧状态 + 本次增量」合并时残留上一轮结论；状态文件写入失败只告警不抛错。

### 客户端 `lib/client.js`

- 手写 bundle（`window.__ModuleLoader__.load`），**无构建步骤**，只 `require('react')`。
- 注册到 `shell.overlay`（root 级 list slot，整帧最上层且点击穿透，卡片自行声明 `pointer-events`）。
- 卡片内容：分支、`短SHA → 短SHA`、落后提交数、上游提交摘要、checkout 路径。
- 操作：**立即更新 / 稍后 / 重新检查**。
- 检查失败（断网、代理不可用等）同样给出卡片与原因，而不是静默无反应。

### 工程

- `test/` 五个可独立运行的验证脚本（见第四节）。
- `.github/workflows/ci.yml`：node 22 / 24 双版本跑语法检查与**离线**测试。
- `LICENSE`（MIT）、`CHANGELOG.md`、`README.md`、完整的 `package.json` 元信息。

## 三、关键决策与取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| 用 git 而非 npm 判断更新 | 本体是源码 checkout，查 npm 必误报 | 只适用于源码部署形态 |
| 插件自探测系统代理，不改用户 git 配置 | Windows 上 git 不读系统代理，而这台机器靠代理才能连 GitHub；改全局配置影响面太大 | 多一层探测逻辑；macOS 尚未覆盖 |
| 只做 `git pull --ff-only` | 绝不生成意外 merge commit | 本地有改动或已分叉时直接失败，需人工处理 |
| 写路由要求 loopback | 更新会改动工作区，不能允许局域网任意触发 | 远程/容器场景需另行设计 |
| 客户端手写 bundle、不引入构建 | 包体积小、无工具链依赖，`git` 安装即可直接运行 | 需要手写模块协议样板；不能用 TSX |
| 「每天首次」按自然日去重 | 契合"开机用一下"的节奏，避免每次重启都打扰 | 进程长期常驻时不会自动复查 |
| 单提交历史（发布后压缩） | 隐私审计要求清除历史中的本机路径痕迹 | 丢失细粒度提交历史，故以本文档归档 |

## 五、已知限制

- **更新后需要重新构建并重启**才生效。`git pull` 只推进源码，而 dsh 运行的是构建产物
  （本次实测的上游包含 `release(dsh): 0.1.5-rc.2` 等 134 个提交）。卡片会在成功后明确提示这一点。
- **进程常驻不重启时不会检查**。触发点是"每天首次启动"；可用卡片上的「重新检查」或直接
  `POST /check` 手动触发。
- **宿主端改动需要重启 `dsh web`**：模块被 Node 的 ESM 缓存持有，卸载再重新挂载插件也不会重新
  `import`（实测确认）。客户端半不受此限，刷新页面即可。
- **代理探测只覆盖 Windows 注册表与环境变量**；macOS 的 `scutil --proxy` 尚未覆盖。
- **需要 web profile**：宿主端 `inject: ['webServer']`，无 web 服务的 profile 里会保持 PENDING。

## 六、开发过程时间线

> 本节是归档的核心：仓库为单提交历史，过程只记录于此。

1. **调研同类插件** —— 用 GitHub API 逐个核实 9 款同类插件（星数、最后推送、是否声明有效 `dsh.bundle`），
   确认它们的主程序检查**全部基于 npm registry**。
2. **确认本机形态** —— 发现 `@deepseek-ai/dsh` 是指向源码 checkout 的 **Junction**，
   `git remote` 为 `deepseek-ai/deepseek-harness`，本地 HEAD 落后上游。据此否定了现成插件方案。
3. **摸清插件 API** —— 读 DSH 一方源码与已装第三方插件，确定：
   `ctx.webServer.register({kind, path, handler})`（原生 req/res）、
   `window.__ModuleLoader__.load({id, factory})`（手写 bundle 格式）、
   `shell.overlay` 为 root 级 list slot、`exports.inject` 是**服务名**而 `dsh.client.inject` 是**包名**。
4. **实现宿主端与客户端** —— 检测、状态持久化、路由、loopback 网关；卡片与三个操作按钮。
5. **三层测试** —— 端到端（本地 bare 仓库，不依赖外网）、客户端渲染（stub react）、路由与安全网关。
6. **安装并真机验证** —— 复制到 profile 并在真实 dsh 上确认路由可用、检查链路跑通。
7. **发现代理问题** —— 真机上检查失败，定位到 **git 不读取 Windows 系统代理**（系统代理在监听，
   但 `git config --global http.proxy` 为空）。验证：`curl` 直连、`git -c http.proxy=… ls-remote`
   成功、无代理 `git` 超时。
8. **改为插件自探测代理** —— 按"不改动用户 git 配置"的约束实现，并加失败回退直连。
   真机验证：`检测到系统代理 → 上游有 134 个新提交 → viaProxy: true`。
9. **修掉两个真实 bug** —— 真机运行暴露「快照 = 磁盘状态 + 本次增量」的字段残留：
   成功结果里带着上一轮的失败 `message`/`hint`；反过来失败时残留 `behind`/`subjects`。
   改为每次检查返回同一组字段，并补了回归测试。
10. **上线 GitHub** —— 本地提交、作者邮箱改为 GitHub 隐私邮箱、VS Code 发布、补齐仓库元信息
    （description、6 个 topic、LICENSE）、新增 CI。
11. **隐私审计与历史清理** —— 全量扫描当前文件 + 完整 git 历史，结论：**无任何密钥/凭证/真实 IP/
    本机用户名**；仅存真实姓名、本地目录路径、代理端口三类痕迹。随后清理内容并重写历史，
    最终压缩为单个提交、作者名改为用户名。
