## 一、这一版要解决的问题

v0.1.0 只认一种部署形态：**源码 checkout**。它把 `@deepseek-ai/dsh` 解析到真实路径，
上溯到含 `.git` 的目录，然后拿 git 判断上游有没有新提交。这对本机的 junction 布局是对的。

但它有两个绕不开的缺口：

1. **别的形态进不来** —— `npx @deepseek-ai/dsh web` 装出来的是预构建包，落在
   `%LOCALAPPDATA%\npm-cache\_npx\<hash>\node_modules\@deepseek-ai\dsh`，**没有 `.git`**，
   git 检测无从下手；npm 全局或项目内安装同理。这类用户拿到插件后会发现它一直"检查失败"。
2. **打扰控制太粗糙** —— 只有「稍后（当天不再问）」。想推迟一周没有出口；反过来，
   进程长期常驻时，触发点仍旧是"每天首次**启动**"，不重启就永远不检查。

于是 v0.2.0 的两条主线是：**认清部署形态**、**把"什么时候打扰你"交给你**。
顺带补上第三件事 —— **更新要能退回去**：既然插件会替你改工作区（`git pull` 或 `npm install`），
就必须给一条可靠的回退通路。

## 二、交付内容

### 部署形态识别

按以下顺序判定，得到 `source` / `npx` / `npm`（`global` 或项目内）三类形态：

- 优先用 `process.argv[1]` —— 它才是**真正在跑的那份 bin 入口**，对源码启动、`npx` 启动、
  全局安装都成立；
- 拿不到时回退到 `$DSH_HOME/profiles/**/node_modules/@deepseek-ai/dsh` 的 `realpath`，
  再上溯找 `.git` 或最近的 `package.json`。

形态决定**检测源**与**更新动作**：

| 形态 | 检测源 | 更新动作 |
|---|---|---|
| 源码 checkout | git 上游提交 | `git pull --ff-only` |
| npx 缓存 | npm registry | 在缓存目录 `npm install` |
| npm 安装 | npm registry | `npm install`（`-g` 视安装位置） |

### 宿主端 `lib/index.js`

- **每日本地 24 时检查**：到点自动检查；若那时 dsh 没开着，启动后**补检**当天遗漏的一次。
  同一自然日只检查一次。快照新增 `nextCheckAt`，展示下次检查时间。
- **registry 比对**（npx / npm 形态）：直连优先、失败自动走 HTTP CONNECT 代理，比对发布通道
  （`latest` / `next` / `alpha`）的目标版本；版本比较正确处理 rc / alpha 预发布排序。
- **更新执行**：源码形态 `git pull --ff-only`（绝不生成意外 merge commit）；非源码形态
  `npm install @deepseek-ai/dsh@<目标版本>`。Windows 上 `spawn` 需要 `shell: true`，
  因此**所有参数先过白名单校验**再拼命令。
- **更新前记录回退点** + 更新后生成**不依赖 dsh 运行**的回退脚本
  （`$DSH_HOME/dsh-rollback.cmd|sh`）—— dsh 若起不来，插件自己也跑不起来，回退入口必须落在 dsh 之外。
- **回退**：`POST /rollback` 回退到更新前那一刻；`POST /rollback?target=<提交号|版本号>`
  回退到用户自选的目标；`GET /rollback/targets.json` 列出候选（源码形态逐个读取该提交自己的
  `package.json` 版本号展示，npx / npm 形态取历史版本）。
- **延期**：`POST /snooze?days=N`（1–30，服务端强制上限一个月，`days=0` 取消）。
- **两半自检**：宿主半与客户端半各带一个 `CODE_VERSION`，接口把它带进快照，客户端比对后提示
  「宿主端改动需要重启 dsh web，仅刷新不够」。
- **路由共 7 条**：`status.json`(GET) / `check` / `update` / `dismiss` / `snooze` / `rollback`(POST)
  / `rollback/targets.json`(GET)。所有写操作要求 loopback 来源。

### 客户端 `lib/client.js`

- 仍然是手写 bundle、**无构建步骤**、只 `require('react')`。
- `shell.overlay` 卡片：**常驻**的「手动检测更新 / 立即更新 / 延期… / 回退…」，
  其中延期与回退不再依赖"存在可用更新"；自动检测只在**真有更新**时弹卡片。
- `settings.section`（设置 → **更新**）：常驻状态框（状态徽标、安装方式、版本 / 分支、
  上次与下次检查、包位置）、**常驻结果行**（含「已是最新」）、手动检测按钮、延期选项
  （含取消）、以及三段式的回退流程（入口 → 目标列表 → 明确写出目标的二次确认）。

### 工程

- `test/` **7 个可独立运行的脚本**（见第四节），全部离线、进 CI。
- `CHANGELOG.md` / `ROADMAP.md` / `docs/releases/` 发布归档体系。
- 环境变量共 4 个：`DSH_GIT_UPDATE_NOTIFIER_ROOT`（独占 checkout）/ `_PROXY` /
  `_CHANNEL` / `_REGISTRY`。

## 三、关键决策与取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| 按部署形态分流检测源 | 源码 checkout 查 npm 必误报；npx / npm 形态没有 `.git` 可查 | 形态判定本身成了最易错的一处，需要专门测试 |
| 形态判定优先 `process.argv[1]` | 它才是真正在跑的 bin 入口，三种启动方式都成立 | 拿不到时仍需回退到 profile 链接探测 |
| 触发点用"本地 24 时 + 启动补检" | 常驻进程也能收到提醒，午夜没开机也不会整天漏检 | 多一个定时器与"今天是否已检查"的状态 |
| 延期上限一个月，且**服务端**强制 | 前端选项可被改，上限必须由服务端兜住 | 想延期更久只能重新操作 |
| 「延期」「回退」按钮常驻 | 功能不该和"当前是否有更新"绑死 | 卡片按钮变多，需要克制样式 |
| 回退走"状态记录 + 独立脚本"双通道 | dsh 起不来时插件也起不来 | 多一个落盘脚本与状态字段 |
| 回退目标也用版本号展示 | 提交号对用户没有信息量 | 每个候选多一次 `git show`（本地，可忽略） |
| 两半各带 `CODE_VERSION` 并强制一致 | "宿主改了要重启"是本插件最容易困惑的点 | 每次改动要同步 bump 两处，漏一处测试就红 |
| 只做快进合并 | 绝不生成意外 merge commit | 本地有改动或已分叉时直接失败，需人工处理 |

### 真机验证

- 运行中的 dsh 上确认：`GET /dsh-git-update-notifier/status.json` 返回 200，
  设置 → 更新区块渲染正常，手动检测可用。
- **尚未验证**：`GET /rollback/targets.json` 的真机表现 —— 宿主端新增路由需要**重启 `dsh web`**
  才注册得上（Node 的 ESM 缓存持有已加载模块），本次发布未重启。该路径已由
  `e2e-local-repo.mjs` 第 10 节在真实 git 仓库上覆盖。

## 五、已知限制

- **更新后需要重新构建并重启**才生效。`git pull` 只推进源码，而 dsh 运行的是构建产物；
  卡片在成功后明确提示这一点。
- **宿主端改动需要重启 `dsh web`**：ESM 缓存不会因卸载重挂而重新 `import`。
  两半自检正是为提示这一点而存在。
- **只做快进合并**：本地有未提交改动或分支已分叉时失败，不自动处理。
- **回退是"就地换版本"，不是无损撤销**：源码形态回退会让工作区 checkout 到旧提交；
  npx / npm 形态回退会重新 `npm install` 旧版本。
- **代理探测只覆盖 Windows 注册表与环境变量**；macOS 的 `scutil --proxy` 尚未覆盖。
- **需要 web profile**：宿主端 `inject: ['webServer']`，无 web 服务的 profile 里保持 PENDING。

## 六、开发过程时间线

自 `v0.1.0` 起的 16 个提交，按发生顺序：

1. **归档 v0.1.0、准备 v0.2.0**（`7a9e037`）—— 把 v0.1.0 的开发过程写进
   [v0.1.0.md](v0.1.0.md)，因为仓库是单提交历史，过程只存在于文档里。
2. **支持 npx / npm 安装形态**（`15a6a3f`）—— 本版最大的结构变化：新增形态判定、
   registry 比对与 `npm install` 升级路径，宿主端从"只认 git"变成"按形态分流"。
3. **把 semver 与 npm-layout 纳入 `npm test` 与 CI**（`aa6d851`）—— 新代码有了回归保护。
4. **每日检查改到本地 24 时**（`f9d7b96`）—— 从"每天首次启动"改为到点触发 + 启动补检。
5. **三处收尾修正**：e2e 断言跟着日志文案改（`728ce9a`）、下次检查时间按本地时间打印
   （`05a8693`）、`status.json` 的形态字段改为取自实际探测结果（`cd0da9e`）。
6. **设置页「更新」区块 + 手动检测**（`083ff9e`）—— 接入 `settings.section` 席位，
   让"随时想看"不必等卡片。
7. **源码形态展示从提交号改为版本号**（`65e70ca`）—— 上游版本从 `FETCH_HEAD` 的
   `package.json` 读取，"落后几个提交"反而成了辅助信息。
8. **延期更新**（`51f5a1c`）→ **可取消延期**（`533a9df`）。
9. **两半自检 + 更新回退**（`f5a6a1f`）—— 自检提示"宿主端要重启"，
   回退则给出状态记录与独立脚本两条通道。
10. **检测结果提示**（`07a500f`）—— 手动检测后不再只是状态悄悄变化；
    「已是最新」也有一条常驻结论；自动检测则只在真有更新时才弹卡片。
11. **延期按钮改为常驻**（`7e30b72`）—— 功能与"当前是否有更新"解绑。
12. **自选回退目标**（`8320525`）→ **目标改用版本号展示**（`49075f3`）——
    回退不再只有一个点，且候选直接显示版本号；非法 target 的校验被提到形态探测之前，
    因此在任何环境下都稳定返回 400 而不是 500。
