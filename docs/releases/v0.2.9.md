## 一、这一版修的是什么

v0.2.8 让插件能更新自己，但**用错了工具**。

`applySelfUpdate` 的 npm 分支一律执行 `npm install`：

```js
const result = await runNpm(['install', spec], cwd, proxy)
```

而它的目标 `cwd` 是 dsh 的 **profile** —— 那里是 **pnpm** 的地盘：

```
~/.dsh/profiles/web/
├── pnpm-workspace.yaml      # packages: [.] / nodeLinker: hoisted
├── pnpm-lock.yaml
└── node_modules/.pnpm/      # pnpm 的存储布局
```

在 pnpm 管理的目录里跑 `npm install`，代价是打乱 `node_modules` 结构、写出一份与 pnpm
互不认识的 lockfile。**功能上"更新成功"了，profile 却成了混合状态** —— 这类损坏往往
要等下一次 `dsh plugin add` 才暴露。

这个缺陷是在准备"回退版本、验证自更新链路"时读代码发现的：本机上 `pnpm-workspace.yaml`
明明白白摆在那里，而那段代码从没看它一眼。

## 二、修法

按目录判定包管理器，再决定用谁：

| 判定依据 | 用哪个 | 命令 |
|---|---|---|
| 有 `pnpm-workspace.yaml` 或 `pnpm-lock.yaml` | pnpm | `pnpm add <spec>` |
| 其它（npx 缓存、普通 npm 项目） | npm | `npm install <spec>` |

判定逻辑抽成导出的 `packageManagerFor(dir)` —— 它属于"选错就出事"的那种决策，必须能被
测试直接盯住：`test/local-check.mjs` 第 12 节覆盖了 pnpm 两种元数据、普通目录、空路径、
未提供路径共五种输入。

失败提示也一并改好：给出与所选管理器一致的手动命令，并附 `dsh plugin add` 作为兜底 ——
后者还能处理 pnpm 11 的 `minimumReleaseAge`（新发布的包会被默认拦截，
`dsh plugin add` 会自动加豁免，而我们自己的 `pnpm add` 不会）。

### 真机验证方式（结论待重启后确认）

这一版的 `pnpm add` 路径需要**重启 `dsh web`** 让新版宿主生效，才能真跑一次。做法是：

1. npm 上已有真实的 `0.2.8`，把 profile 降到它：`dsh plugin --profile web add dsh-git-update-notifier@0.2.8`
2. 重启 `dsh web` —— 此时宿主是 0.2.9，它检测到本地 `0.2.8`
3. 设置页点「更新插件」，观察宿主是否走 `pnpm add dsh-git-update-notifier@0.2.9`

这一路径**尚未在真机跑过**，所以第 3 步的结论在这份归档里先留空；跑通（或跑不通）之后
再回填。

## 四、留给下一版

`installStagedPackage`（更新 **dsh 本体**）仍固定使用 npm。它面向的形态是 npx 缓存与
npm 安装目录，那些确实是 npm 管的，所以当前行为没错；但如果哪天要支持"pnpm 项目里装的
dsh 本体"，那里也要套用同一个 `packageManagerFor`。
