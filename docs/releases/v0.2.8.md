## 一、这一版要解决的问题

从 v0.2.0 到 v0.2.7，插件学会了识别 dsh 的三种部署形态、按时检查、断点续传、装前校验、
失败重试、失败回退、失败诊断 —— 唯独没有学会一件事：**检查它自己**。

于是出现一个别扭的局面：一个专门提醒你"dsh 有新版本了"的工具，自己停在旧版本上不会吭声。
发现这个问题的方式也很直接：使用者注意到插件检测不到自己的更新。

难点不在"比较两个版本号"，而在**它自己是怎么被装进来的**。以本机为例：

```
~/.dsh/profiles/web/node_modules/dsh-git-update-notifier   # 普通目录，不是 junction
  ├─ 没有 .git                        → 不是 git 检出
  └─ profile 的 package.json 里没有它  → 也不是 npm / github 依赖
```

也就是说，它是一份**被手工复制进去的副本**。对这类副本，"去哪儿问最新版本"这个问题
没有现成答案 —— 而这恰恰是最需要覆盖的情形。

## 二、交付内容

### `lib/selfcheck.js`（新增）

- **自身定位**：从 `import.meta.url` 推出自己的包目录，读自己的 `package.json`
  得到版本号与 `repository`（解析出 `owner/repo`）。
- **宿主根判定**：区分普通 `node_modules` 布局与 pnpm 的
  `node_modules/.pnpm/<pkg>@<ver>/node_modules/<pkg>` 布局。
- **安装形态判定**：

  | kind | 判定依据 | 远端来源 | 能否自动更新 |
  |---|---|---|---|
  | `checkout` | 自己所在目录（或上溯）有 `.git` | git 上游 | 能 |
  | `npm` | 宿主清单声明为本包（semver） | npm registry | 能 |
  | `github` | 宿主清单声明为 `github:` / git URL | GitHub | 能 |
  | `manual` | 目录在，但没有任何声明 | GitHub 兜底 | 否（见下） |
  | `unknown` | 连自己的 `package.json` 都读不到 | — | 否 |

- **远端查询**：`fetchGithubLatest` 先查 **release**（语义明确），查不到再退到 **tags**
  （本仓库每个版本都打了标签，所以这一层同样可靠），并剥掉 tag 的 `v` 前缀。

### 宿主端接入

- 每次检查都会**顺带**查一次自身更新，写进快照的 `selfUpdate` 字段。
  它失败只记一条日志 —— **绝不影响 dsh 本体的结论**（一个是网络问题，不该污染另一个）。
- **`POST /plugin/update`**：按形态分流更新插件自己。
  - `checkout` → `git fetch` + `merge --ff-only`（与 dsh 本体同一条路，同样可重试）
  - `npm` / `github` → `npm install <包名>@<版本>` 或 `npm install github:<仓库>#v<版本>`
  - `manual` / `unknown` → **明确拒绝**并给出做法
- 更新的是宿主端代码，所以提示里写明需要**重启 `dsh web`**。

### 客户端

设置页多一行「插件自身已是最新（X）」或「插件自身有新版：X → Y（来源）」；
可自动更新时多一个「**更新插件**」按钮（与 dsh 本体的「立即更新」是分开的两个动作）。

### 工程

- `npm test` 增至 **10 个脚本**：新增 `test/selfcheck.mjs`。
- 新增环境变量 `DSH_GIT_UPDATE_NOTIFIER_GITHUB_API`：既能指向国内镜像，
  也让测试可以注入本地 http server 来离线验证查询与回退。

## 三、关键决策与取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| 先判安装形态，再决定"问哪里" | 不判形态就只能假定一种来源，其余情形全落空 —— 而本机恰好是落空的那一种 | 四种形态 × 各自的失败路径，代码与测试都变多 |
| GitHub 始终兜底 | 手工副本除了 GitHub 无处可问；这是它唯一能覆盖的情形 | 未认证 API 每小时 60 次限额（一天查一次，够用） |
| 手工副本**不做**自动更新 | "不知道这份副本从哪来"时替换它，风险大于收益；宁可让用户多做一步 | 这类安装的用户要手动更新（插件给出手动命令） |
| release 优先、tags 回退 | release 是作者显式发布的版本，语义最明确；但仓库没建 release 时不能就此失败 | 没有 release 时要多一次请求 |
| API 基址可注入 | 测试必须离线（CI 不联网），国内也需要镜像 | 多一个环境变量 |
| 自身检查与本体检查解耦 | 一个失败不该影响另一个的结论 | 快照多一组字段、日志多一类输出 |

## 四、验证记录

### 自动化测试（`npm test`，10 个脚本全部通过）

| 脚本 | 本版新增的覆盖 |
|---|---|
| `selfcheck.mjs`（新） | 仓库地址解析 5 例（`git+https` / 字符串 / SSH / 缺失 / 非 GitHub）；自身定位与版本；依赖声明读取（semver、`github:`、`devDependencies`、pnpm 布局）；当前工作副本的形态判定；GitHub 查询三条路径 —— release 优先并剥 `v` 前缀、无 release 时回退 tags、两者都失败时给出原因；空仓库地址直接拒绝 |
| `local-check.mjs` | **12 条**路由；第 11 节：`/plugin/update` 在没有可更新版本时 409、非本机 403、GET 405；快照带出 `selfUpdate` 字段 |
| `client-render.mjs` | 第 15 节：显示「插件自身有新版」与来源、可自动更新时给出「更新插件」且点击打到 `/plugin/update`；不能自动更新时不显示该按钮但给出手动做法；「已是最新」时如实显示 |
| `e2e-local-repo.mjs` | 真实跑通了自身检查这条线 —— 测试输出里可见 `插件自身已是最新（0.2.7）`（该仓库是 git 检出，走的是 git fetch 分支） |

### 尚未在真机验证的部分（如实记录）

- **本机实际安装的那份是 `manual` 形态**，所以"手工副本 → GitHub 兜底检测"这条路径是
  逻辑上最该被验证的一条，却**没有在真机上跑过**（需要重启 `dsh web` 让新版宿主生效）。
  它由 `selfcheck.mjs` 的形态判定用例与 GitHub 查询用例分别覆盖，但没有端到端连起来跑过。
- `POST /plugin/update` 的三条自动更新路径同样未在真机验证：本机是 `manual` 形态，
  按设计会拒绝自动更新。

## 五、已知限制

- **手工副本不能一键更新**（按设计）。这是本机当前的形态，插件会给出
  `dsh plugin add github:lmr233/dsh-git-update-notifier` 这样的建议。
- **GitHub API 有未认证限额**（每小时 60 次）。插件一天只查一次，但如果频繁手动检测，
  理论上可能遇到限流 —— 届时会如实报错而不会静默。
- **不判断"远端是否领先但版本号没动"**。检测以版本号为准：如果上游只是改了代码而没有
  提升 `package.json` 的版本号，插件会认为"已是最新"。这是刻意的 —— 对使用者来说，
  版本号才是"该不该更新"的语义。
- 自我更新仍然是宿主端改动，需要重启 `dsh web` 才生效。

## 六、开发过程时间线

1. **先看现场**：读本机安装目录，确认它是普通目录、没有 `.git`、且 profile 的
   `package.json` 里没有声明 —— 于是明确了"必须有 GitHub 兜底"这个前提。
2. **写 `lib/selfcheck.js`**：把"自己在哪里、怎么被装的、去哪儿问版本"三件事收在一个模块里，
   全是纯本地读取加两个只读网络查询（不修改任何东西，便于测试）。
3. **形态判定**：`checkout` / `npm` / `github` / `manual` / `unknown` 五种，
   每条都有明确的"判不出来时怎么办"。
4. **远端查询与兜底**：release 优先、tags 回退；`manual` 形态直接走这条路。
5. **接入宿主端**：`inspectSelf` 组合形态 + 远端 + 版本比较；`applySelfUpdate` 按形态分流；
   在每日检查里顺带调用，并用 try/catch 把它与 dsh 本体的结论**彻底解耦**。
6. **新路由 `POST /plugin/update`**（12 条），`manual` 形态返回 409 并附带手动做法。
7. **客户端**：状态行 + 独立的「更新插件」按钮；进度轮询条件从 `busy === 'update'`
   放宽到也包含 `plugin-update`。
8. **测试**：先写 `selfcheck.mjs`（含用本地 http server 冒充 GitHub API 的三条路径），
   再补 `local-check` 与 `client-render`，最后两处路由数 11 → 12。
9. **修掉一个自己造成的缺陷**：客户端里 `var selfInfo` 原本声明在 `status !== null` 分支内，
   而按钮区在分支外引用它 —— `status` 为空时就成了 `undefined` 并抛错。
   改成在块外定义、并显式兜 `null`。
